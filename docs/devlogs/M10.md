## 2026-10-11 · 제출 전 독립 리뷰와 재검증

## 2026-10-11 · 원본 화면 전체 이식과 제품 빌드 교차 검증

사용자가 iPhone Simulator의 모든 화면이 원본과 다르다고 지적했다(2026-10-10). 원본 HEAD의 레이아웃 XML·문구·치수·색·아이콘과 원본 README 화면(2024-07판)을 근거로 홈·산책·산책 완료·산책 모아보기·도장 목록/상세·마이페이지·반려견 목록/상세/폼·알림·로그인·회원가입을 공통 Compose로 다시 만들었다. README 사진과 현재 XML이 다른 곳(도장 목록)은 현재 XML을 따랐다. 범위·대안·포기한 것은 [ADR-013](../adr/013-original-ui-port-scope.md), 화면별 같은 점과 다른 점은 [패리티 표](../ui-parity.md)에 있다. 구현에 앞서 ADR을 먼저 썼고 실제 지도·로그인 동작·날씨·알림 예약·사진·여러 마리는 범위에서 뺐다. 화면에도 "연결 전"으로 표시한다.

**데이터와 도메인.** Room v4→v5로 `dogs`에 `gender/age/breed/memo`(모두 nullable)와 `deleteDog`를 더했다. 기존 v4 행의 성별은 추정하지 않고 비워 두며 이 경우를 `PersistenceTest`가 검사한다. 도장 8종·주간 달성률·일/월 거리·"N 시간 전"·표기 규칙은 저장 없이 산책 이력에서 계산하는 순수 함수다(`Stamps.kt`, `WalkStats.kt`, `WalkFormat.kt`). 같은 이력이면 언제나 같은 결과라 앱을 다시 열어도 도장이 흔들리지 않는다. 경계 값(일 합계 1.5km 정확히·월/주 경계·연속일·주 7회·주 10/15/20km)은 `commonTest`의 단위 테스트로 고정했다.

**실제 실패와 수정**
- Kotlin/Native가 JVM 전용 `toSortedSet`을 거부했다. JVM·Android는 통과했고 iOS 링크에서야 드러나 `distinct().sorted()`로 바꿨다.
- 원본 `img_sample_mini_map.png`는 빨간 경로가 이미 그려진 이미지였다. 그 위에 저장 경로를 그리면 선이 두 겹으로 보여, 경로 없는 큰 샘플 지도를 모든 지도 화면에 자르기로 쓰고 mini 자산은 지웠다.
- 2배 글씨 시나리오가 고정 높이 때문에 글자를 자르는 곳을 찾았다: 산책 버튼, 하단 탭(80dp), 반려견 행(140dp), 로그인 입력(55dp), 앱바 제목과 우측 액션. 모두 최소 높이로 바꾸거나 제목이 양옆 슬롯 사이에서 줄바꿈하게 했다.
- 가로 넘침 검사가 가운데 정렬 글자를 오탐했다. 줄 오른쪽을 노드가 아니라 문단 폭과 비교하게 고쳤다. 원본이 한 줄 말줄임을 의도한 반려견 이름만 `ellipsized-by-design`으로 제외했다.
- 차트 글자를 sp로 그리면 2배에서 라벨이 겹쳤다. 원본(MPAndroidChart)처럼 dp 기준으로 맞췄다. 어두운 모드에서 선택 안 된 성별 칩이 읽히지 않아 `blackWhite` 토큰을 더했다.
- 옛 iOS 제품 테스트가 합쳐진 접근성 라벨로 버튼을 못 찾았다. 새 화면에는 `testTag`/`contentDescription`을 직접 지정했다.
- 새 상수 `STAMPS_PER_WEEK`가 Swift에 공개되는 API로 나타나 `@HiddenFromObjC`로 숨겼다(`docs/api/SharedApp.h` 기준선 불변).
- macOS가 `/tmp`의 오래된 파일을 지워 iOS 호스트 빌드 폴더의 SwiftPM 체크아웃과 Xcode 중간 산출물이 깨졌다(`Package.swift cannot be accessed`, `.pcm not found`). 소스 문제가 아니었다. 해당 폴더의 `SourcePackages`와 `Build`·`ModuleCache.noindex`를 지우고 패키지를 다시 해석하자 복구됐다. 이 때문에 전체 검사의 릴리스 가드 단계가 한 번 실패했다.

**제품 빌드에서 직접 확인.** 시나리오(`개발용 예시 데이터`) 빌드가 아니라 일반 제품 빌드를 Android 에뮬레이터(Pixel 4a, API 34)와 iPhone 17 Pro Simulator(iOS 26)에 설치했다. 첫 실행 → 반려견 등록(이름·성별·나이·견종) → 산책하기 → 좌표 주입(Android 초당 약 11m로 141개, iOS `simctl location`으로 약 1.7km) → 정지 → 산책 끝! 순서를 화면 조작으로 진행했다. 두 플랫폼 모두 산책 완료 화면의 시간·거리가 맞았고 "오늘의 산책 완료" 도장 다이얼로그가 떴으며 홈 그래프의 오늘 점, "14개 중 1개 획득", 산책 모아보기 카드와 경로 팝업, 도장 목록·상세의 획득 일시, 마이페이지와 반려견 목록의 저장 값(성별)이 이어졌다. Android 1.5km(2분 34초), iOS 1.7km(4분 50초). 결과 화면과 영상은 [`docs/evidence/submission/`](../evidence/submission)에 있다. 좌표는 에뮬레이터·시뮬레이터에 넣은 값이며 야외 실측이나 실기기 결과가 아니다. 이 확인은 구현자의 육안·조작이고 독립 리뷰가 아니다.

**검증.** 소스를 멈춘 상태에서 필수 검사 6개(공통 테스트·Android 시나리오·iOS 시나리오·화면 캡처 수집·Release 가드·모듈 경계)를 한 번에 돌려 모두 통과했다: 공통 Kotlin JVM+iOS 84개, Android 시나리오 계측 5개, iOS 시나리오 XCTest 7개(실패·skip 0), 실제 화면 캡처 Android 57장+iOS 57장, 시나리오 fixture 유출 0건·거부 guard 3개, 모듈 경계 통과. 같은 소스에서 일반 제품 빌드 검사도 다시 돌렸다: Android 제품 계측 2개, iOS 제품 XCTest 2개, iOS Core Location 좌표 주입 1개가 모두 통과했다. 전부 에뮬레이터·시뮬레이터 결과이고 독립 리뷰 기록은 아직 없다.

**남은 것.** 실제 지도 타일(Android Naver Map·iOS MapKit), 로그인·계정 격리, 여러 마리·사진, 백그라운드 위치, 날씨·알림 예약, 서명 배포·실기기 검증은 이번 범위가 아니다. 독립 리뷰 기록도 아직 없다.

## 2026-10-10 · foreground Core Location 연결

원본 UI에 가까운 로컬 시연에서 Android만 실제 foreground 위치를 저장하고 iOS는 시간만 저장하는 차이가 있었다. 사용자가 남은 앱 범위를 계속 구현하라고 요청하고 세부 기술 선택을 위임했다. [ADR-012](../adr/012-ios-foreground-location.md)에 따라 iOS 호스트의 `CLLocationManager`와 When In Use 권한, 공통 산책 ID/segment 관찰·표본 제출 경계, 기존 Room 검증/트랜잭션을 연결했다. 대안인 Kotlin/Native 직접 Core Location 바인딩은 Swift 호스트가 이미 앱 수명과 네이티브 SDK를 관리하므로 이번 변경의 경계를 늘린다. Always 권한·배경 모드 도입은 기기 잠금과 배터리/권한 회귀를 동반하므로 이번 변경에 포함하지 않는다.

반례는 권한 거절, 앱 inactive/background, 오래된 위치 callback, 산책 재개 뒤 이전 segment callback이다. 리스너는 앱이 활성화되고 Recording일 때만 시작하고, 권한 거절 시 시간 기록 안내를 띄운다. inactive/background 또는 산책 종료에는 업데이트를 중단한다. background에서 기존 런타임이 산책을 중단한다. Swift 구독 취소와 `closed` guard 뒤에도 Room의 산책 ID·구간 시작 시각·정확도/속도 검증을 마지막 방어선으로 유지한다. Debug UI 테스트의 권한 대화상자 우회 인자는 Release에서 제외한다. 합성 경로는 별도 DB로 남는다.

현재 검증: 공통 39개 테스트(새 관찰/취소·입력 경계 2개 포함), Android APK·iOS KMP framework, iOS 제품 XCTest 2개와 Android 제품 계측 1개, Android 시나리오 3개가 통과했다. iOS 시나리오 5개와 unsigned Release guard, 실제 시뮬레이터 위치 주입 결과는 별도 확인 중이다. 자동 UI 테스트는 권한 대화상자를 비활성화한 로컬 DB 흐름이므로 Core Location 실제 callback 성공으로 세지 않는다. 실제 iPhone의 위치 정확도, 권한 철회, 잠금/배경, MapKit 지도는 아직 미검증/미구현이다. M10 전체 티켓은 열어 둔다.

교차 검증에서 `AppModel`이 새 runtime을 화면에 공개하기 전에 위치 드라이버를 만들도록 순서를 고쳤다. 초기 순서는 화면의 `onAppear`가 드라이버 생성보다 먼저 도착할 가능성이 있었다. iOS 시나리오 첫 전체 실행은 5개 중 4개가 통과했고, 합성 경로의 설명을 `실제 좌표`에서 `저장된 좌표`로 고친 뒤 XCTest가 이전 문구를 기대해 1개가 실패했다. 실제 실패 줄과 새 UI 문구를 대조해 기대값을 바꾼 뒤 해당 XCTest 1개를 별도로 재실행해 통과했다.

두 번째 시나리오 XCTest는 실제로 5개 모두 성공·skip 0이었다. 실행 도중 별도 `DDARAOGAE_LOCATION_TESTS` 전용 테스트를 추가해 실행 당시의 Python runner가 소스에서 예상 테스트를 6개로 계산했고, 원본 xcresult가 `totalTestCount=5/result=Passed`인데도 집계 `complete=false`가 됐다. 테스트 실행 실패와 집계 입력 변경을 구분한다. runner는 위치 전용 조건부 메서드를 일반 개수에서 제외하도록 수정했고, 현재 입력으로 시나리오를 다시 실행해야 `complete=true`를 기록한다. 위치 전용 검사는 Simulator 권한 부여와 보행 경로 주입 뒤 실제 callback 2개 이상·0m 초과 거리·종료 후 기록 화면을 요구한다. 아직 그 결과를 성공으로 세지 않는다.

첫 위치 전용 XCTest에서는 표본 2개 이상과 0m 초과 거리, 완료 후 기록 화면까지 도달했다. 다만 새 UI 테스트가 화면 아래 64pt 탭바의 `산책` 버튼에 일반 콘텐츠 버튼용 여백 조건을 적용해 두 assertion이 실패했다. 접근성 트리에서 버튼이 화면 y=818~866에 있는 것을 확인했다. 기존 제품 테스트와 같은 직접 탭으로 수정하고 동일한 Simulator 경로를 다시 실행한다. 이 첫 실행은 Core Location→Room 흐름의 관찰 근거이지만 전체 테스트 PASS가 아니다.

탭 좌표 수정 뒤 별도 위치 검사는 1개 통과·skip 0이었다(`.workflow/M05/swift-location-tests.json` 원본 xcresult). 화면의 `위치 2개 이상 기록 중`과 0m 초과 거리, 종료 후 저장 기록을 확인했다. 첫 첨부 화면은 Compose 전환 중 캡처돼 카드가 옆으로 밀려 있었다. 제품 오류와 구분하기 위해 화면 제목의 x 위치가 정상으로 돌아온 뒤 촬영하게 테스트를 고쳤고 같은 위치 검사가 다시 1개 통과했다. 안정화된 화면을 직접 열어 카드/버튼 배치가 정상임을 확인했다. 지도 설명은 마지막 한 글자만 둘째 줄로 넘어가므로 `샘플 지도 위 상대 이동선 · 실제 위치와 다름`으로 줄였다. Android 시나리오 3개와 제품 1개, 공통 39개, iOS 제품 2개, Swift API, 현재 소스의 unsigned Android/iPhoneOS Release guard·아카이브·dSYM이 통과했다. 최종 문구의 iOS 시나리오/위치 재검사와 PNG 교체는 진행 중이며 그 전 결과를 최종 화면 증거로 쓰지 않는다.

짧아진 지도 설명의 Android/iOS 시나리오 3개씩과 iOS Core Location 위치 주입 1개가 성공했다. 최종 위치 검사는 정상 상태로 돌아온 완료 화면의 첨부 PNG를 남겼고 8m 저장 거리가 보인다. Swift 드라이버 자체 검토에서 산책 종료 후 늦은 `didFailWithError`가 안내를 다시 띄울 수 있는 경로를 막았다. 이 마지막 수정 뒤에도 위치 주입 1개와 unsigned iPhoneOS archive/fixture guard가 통과했다. 화면은 육안으로 카드 위치·지도 설명·버튼을 확인했다.

Android 제출 화면을 현재 APK에서 다시 찍으려고 에뮬레이터에 제품 빌드를 설치했다. 새 로컬 DB로 Bori를 등록한 뒤 첫 37.5/127.00015 위치를 확인했다. 처음 서울시청 좌표를 주입했을 때에는 출발점에서 수 km 떨어져 속도 필터가 거부했고 1개/0m가 유지됐다. 저장된 첫 좌표 인근의 3개 보행 지점을 다시 주입하자 Room에서 4개 표본과 화면 21m를 확인했다. 종료 후 화면이 여전히 `기록 중`이라고 말하는 상태 문구 오류를 발견해 Recording에만 그 문구를 쓰고 나머지 상태는 `저장됨`으로 바꿨다. 앱을 다시 설치한 뒤 이력에서 저장된 21m와 짧은 지도 설명이 현재 화면에 그대로 복원됨을 확인했고 새 [Android 기록 PNG](../evidence/submission/previous-ui/android-record.png)를 남겼다. 이전 26m 화면은 [별도 이력](../evidence/submission/previous-ui/android-record-26m-previous.png)에 보존했다. PDF를 두 새 플랫폼 화면과 현재 거리로 재생성하고 2쪽 렌더링을 육안 확인했다. 현재 화면 문구 수정 후 공통 39개는 다시 통과했고 남은 플랫폼 회귀는 진행 중이다.

마지막 검증 계획 중 시뮬레이터의 UI 테스트가 `--reset-preview`로 보통 사용자의 `walks.db`를 지울 수 있음을 발견했다. 테스트가 제품 저장 데이터를 바꾸지 않도록 Debug 전용 `walks-ui-test.db`와 `walks-location-test.db`를 분리하고 기존 `walks-demo.db` 경계는 유지했다. 대안인 별도 Simulator 생성은 디스크/설치/운영 시간이 들고 현재 테스트의 DB 수명만 분리하면 충분하다. Release 문자열 검사에 새 테스트 플래그와 DB 이름을 추가했다. 33개 Python 하네스는 통과했고 iOS 제품/위치 UI와 Release binary를 변경 후 다시 확인한다. 디버그 테스트 파일은 실제 제품 DB 및 서버 데이터의 근거로 세지 않는다.

코드 재검토에서 `--reset-preview`만 단독으로 전달하면 일반 `walks.db`를 지울 수 있는 경로가 남아 있었다. 초기화 조건을 합성 경로 또는 전용 테스트 DB 선택 시로 좁혔다. 이 DB 가드 수정 뒤 iOS 제품 XCTest 2개·위치 주입 XCTest 1개가 각각 skip 0으로 통과했고, 위치 검사는 종료 화면의 0m 초과 거리만이 아니라 앱 종료·재실행 뒤 기록 상세의 거리와 상대 이동선 복원도 확인한다. unsigned Android/iPhoneOS Release 검사에서는 새 테스트 인자/DB 표식 유출 0건, 거부 guard 3개, iPhoneOS arm64 archive와 일치하는 dSYM을 확인했다. 이는 서명이나 TestFlight 업로드 증거가 아니다. 마지막 DB 조건 수정이 포함된 iOS 시나리오 5개 전체 재실행은 진행 중이며, 성공 전까지 그 재실행을 PASS로 기록하지 않는다.
